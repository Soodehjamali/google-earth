## Phase B complete — Core engine primitives

Delivered:
- `base.py` — `Metric` ABC + `MetricContext`. Context produces deterministic
  SHA-256 cache keys folding geometry, dates, scale, cloud tolerance,
  dataset versions and metric-specific extras. `can_attempt()` compares the
  request against the primary dataset's coverage window.
- `aggregation.py` — reducer construction (injected `ee` module so the file
  stays import-clean), reduction parsing, coverage arithmetic, weighted
  stats merging.
- `catalog.py` — metric registry with duplicate-key protection, plus the
  public catalog payload.
- `executor.py` — concurrent execution in a bounded thread pool (default 4,
  because Earth Engine enforces quotas), per-metric error isolation, and
  error-message sanitisation that redacts paths, service-account emails and
  PEM blocks.

### Bugs found and fixed in Phase B
1. `SpatialStats` could be constructed inconsistently (valid 50 / total 100 /
   missing 0) because missing fields were only filled by the parser. Coverage
   fields are now derived on construction; a total below the valid count is
   corrected upward.
2. **The executor logged with structlog-style keyword arguments while
   `app/core/logging.py` returns a plain stdlib logger.** `Logger._log`
   rejects unexpected kwargs. This raised TypeError only when a record was
   actually emitted, so it was invisible at INFO level and fatal on error
   paths. Converted all call sites to positional `%s` formatting. Two
   regression tests added: one pins the logger type, one scans call sites
   for `key=value` kwargs. Verified the scanner catches the bug by
   injecting it and watching the test fail.

### Lesson recorded
`app/core/logging.py::get_logger` returns `logging.getLogger(name)` — a
stdlib logger. **Never use keyword arguments with it.** Use `%s` formatting.
The project has `structlog` in requirements but does not actually use it.

## Phase C complete — Vegetation engine

Delivered:
- `indices.py` — 8 pure index formulas (ndvi, evi, savi, msavi, ndre, ndwi,
  ndmi, mndwi) with no Earth Engine dependency, so the maths is fully

- `vegetation.py` — 8 metrics: NDVI, EVI, SAVI, MSAVI, NDRE (Sentinel-2,

- SCL masking helper; median composite; MODIS fill-value masking before
  scaling.

### Bugs found and fixed in Phase C
1. **`NDRE` declared `band_scale = 20` but nothing read it**, so
   `effective_scale` returned the 10 m default. Earth Engine would have
   resampled the 20 m red edge band to 10 m and the provenance would have
   claimed 10 m resolution. `_SpectralIndexMetric` now overrides
   `effective_scale` to return the band scale, so a caller-supplied scale
   cannot override the resolution the bands actually support.
2. Vegetation metrics stated index behaviour as limitations but did not
   state what they cannot determine. Every spectral index now carries an
   explicit non-diagnostic limitation naming drought, waterlogging,
   nutrient shortage, disease, pest damage and management effects as
   indistinguishable.

### Formula facts established by testing
- **SAVI at L=0.5 sits BELOW NDVI** for the same reflectances. The
  `(NIR+RED+L)` denominator attenuates. Exact identity:
  `SAVI = NDVI * (NIR+RED)/(NIR+RED+L) * (1+L)`. With L=0 SAVI == NDVI.
- **The MSAVI radicand `(2*NIR+1)^2 - 8*(NIR-RED)` is never negative across
  the entire physical reflectance domain** (boundary solving gives
  `RED = NIR - (2*NIR+1)^2/8`, which is non-positive for all NIR >= 0). The
  guard in `msavi()` is defensive and only reachable with non-physical
  input such as NIR=-5.6, RED=-20.0.
- NDMI and NDWI take different bands: NDWI is `(GREEN-NIR)/(GREEN+NIR)`,
  NDMI is `(NIR-SWIR1)/(NIR+SWIR1)`. They must never be compared by
  passing identical arguments.

## Phase D — Climate and meteorology engine (complete)

`app/services/agriculture/climate.py` + `units.py`. 10 metrics on
`ECMWF/ERA5_LAND/DAILY_AGGR`, all MODELLED / DERIVED / PROXY.

### Verified meteorological facts
- **Magnus formula verified to 0.11%** against published values:
  0 °C -> 0.6108 vs 0.611 kPa; 20 °C -> 2.3383 vs 2.339; 40 °C -> 7.3756
  vs 7.384. Form used: `es = 0.6108 * exp(17.27*T / (T+237.3))` kPa.
- ERA5 unit conversions confirmed exact: 300 K -> 26.85 °C;
  0.005 m -> 5.0 mm; 25e6 J/m² -> 25.0 MJ/m²; PAR 0.45 -> 11.25 MJ/m².
- `total_evaporation_sum` is **negative for upward flux** (ECMWF treats
  downward as positive). The water balance must negate it.
  `potential_evaporation_sum` sign is INFERRED only, not documented.
- ERA5-Land wind needs `sqrt(u²+v²)`; a single component is not a speed.

### Real defects fixed in Phase D
1. `_reduce_era5_band` reduced the period mean and read per-day values
   from a *separate* computation, so the two could disagree about which
   days were used. Unified to one collection.
2. Per-day read used `map(...).getInfo()`, but the real API returns an
   `ImageCollection` — the flattened list would have been empty. Fixed to
   the documented idiom: `image.set(prop, ...)` then
   `aggregateArray(prop).getInfo()`.
3. `WindSpeedMetric` reduced the eastward component ALONE. A 10 m/s wind
   from the north would have reported 0. Now combines per day.
4. `std_dev` was being put through offset conversions. A spread does not
   take an offset, so it is now dropped unless conversion is scale-only.

### Pairing tests proven effective
Injected an unpaired implementation for VPD and for wind and confirmed
the tests fail: VPD gave 2.325 vs 2.654 expected; wind gave 7.071 vs 10.0.
Both restored afterwards.

idempotent, NOT an import side effect. Returns sorted keys.

## Phase E — Thermal engine (complete)

`app/services/agriculture/thermal.py`. 5 metrics: MODIS `MOD11A2`
day/night/mean LST + day-night range, plus Landsat 8 `ST_B10`.

### THE BIG ONE: scale factor was never applied
`parse_reduction_result` returned **raw stored values**. The registry had
declared `LST_Day_1km` with `scale_factor = 0.02` since Phase A but
nothing read it on the reduction path. MODIS LST came back as ~15000
instead of ~300 K. Fixed by adding an optional `band_spec` parameter that
converts through `BandSpec.to_physical` at this single boundary.
`climate.py` and `thermal.py` now pass it; `vegetation.py` deliberately
does not (it applies the reflectance factor inside the image expression
before computing the index, so passing a spec would double-apply).
7 regression tests added. Confirmed 300 K raw -> 26.85 degC.

### MODIS QC bit layout (verified against the Earth Engine catalog page)
Bits 0-1 mandatory QA, 2-3 data quality, 4-5 emissivity error,
6-7 LST error. Decoded independently because they genuinely disagree: a
pixel can be "produced, good quality" while carrying a 2 K error.
`is_reliable` requires `lst_error_kelvin <= 1.0`.

### Other Thermal facts
- `LST_Day_1km` raw range is 7500-65535 counts (150-400 K physical).
  Raw 0 is the fill; physical 0 K is impossible so there is no clash.
- Landsat `ST_B10` = DN * 0.00341802 + 149.0 K. Verified: 45000 raw ->
  302.8109 K -> 29.6609 degC.
- Landsat thermal is acquired at **100 m**, delivered resampled to 30 m.
  `default_scale` = 100 wins over any caller scale, so provenance cannot
  overclaim.
- New `LANDSAT_THRESHOLDS` preset: the MODIS floor of 5 valid pixels
  would wrongly call a smallholder field insufficient at 100 m.
- `MetricResult` guard caught a real contradiction: the Landsat metric
  computed a value while quality said `insufficient`. Construction raised.

### Canopy temperature prohibition — enforced twice
1. The disclaimer is in each metric's class-level `limitations`, so
   `build_provenance` copies it into every provenance record.
2. `test_the_engine_never_declares_a_canopy_temperature_key` scans every
   `*.py` in the package for `key = "...canopy..."`.

### Gotcha: single-element tuples in limitations
`_CANOPY_TEMPERATURE_DISCLAIMER = ("...",)` is a TUPLE. Putting it into a
`limitations = (...)` tuple nests it, producing
`TypeError: sequence item 0: expected str instance, tuple found` at
render time. They must be plain strings.

**631 passing** (+182 from Phase C's 449), 26 integration tests skipped
by default across both climate and thermal integration files.

### 2. Live catalogue verification — DEFECTS FOUND IN THE EXISTING REGISTRY

Verified against the official GEE Data Catalog on 2026-09-18.

**(a) `MODIS/061/MOD16A2GF` and `MOD16A2` `LE` and `PLE` are declared WRONG.**
Registry says `"J/m2/day"` with `scale_factor = 10000`. The catalog says the
unit is `J/m^2/day` and the stored scale is 10000 — the declared unit is
technically right but the *description* says "8-day average" which the
catalog confirms. **However** the registry's `valid_range = (0.0, 1.0e9)`
is wrong-ish and harmless, while the **`min`/`max` in the catalog are
±32700 (raw)**. The real defect: registry declares
`nodata_values = (32761..32767)` for ALL bands. The catalog states for ET/PET:
"Class assignment in fill values 32761 through 32767 might be inaccurate.
They are not included in the EE assets." So for MOD16A2 the fill values are
**removed from the asset entirely**, not stored. Declaring them as nodata is
therefore harmless but also unnecessary; the genuine MOD16 fill value is
**32767 alone** in the NetCDF, and MOD16 defines 32767 as fill. Keep the
declaration — it is defensive, not wrong. **No change required, but the
caveat text should say the fills are pre-removed.**

**(b) ERA5 `potential_evaporation_sum` sign — now VERIFIED, not inferred.**
The catalog still does NOT state a sign convention for
`potential_evaporation_sum` specifically. The global statement appears only
on `total_evaporation_sum`: "The ECMWF Integrated Forecasting System
convention is that downward fluxes are positive. Therefore, negative values
indicate evaporation and positive values indicate condensation."
→ `potential_evaporation_sum` remains **inferred**. Registry caveat already
says so. **Keep the inference flag; add a regression test that asserts the
inference is still flagged.**

**(c) ERA5 `total_runoff_sum` DOES NOT EXIST.** The catalog lists
`runoff_sum`, `sub_surface_runoff_sum`, `surface_runoff_sum` — there is no
`total_runoff_sum`. If Phase F wanted a runoff metric it must use
`surface_runoff_sum` (+ `sub_surface_runoff_sum` for total). Registry does
not currently declare any runoff band, so nothing is broken — just do not
invent `total_runoff_sum`.

**(d) ERA5 volumetric soil water bands 3 and 4 are MISSING from the registry.**
Registry declares `volumetric_soil_water_layer_1` and `_layer_2` only. The
catalog has all FOUR: layer 1 (0-7 cm), 2 (7-28 cm), 3 (28-100 cm),
4 (100-289 cm). Unit is **volume fraction** (m3/m3), no scale factor.
→ **Add layers 3 and 4** so a root-zone (0-100 cm) integration is possible.

**(e) ERA5 `evaporation_from_vegetation_transpiration_sum` has SWAPPED values.**
Catalog verbatim: "Due to a known issue with ECMWF data, this band has values
corresponding to the evaporation_from_open_water_surfaces_excluding_oceans
band." Same for bare soil and open water. → **Never decompose ET into
components from ERA5.** Registry already records this in caveats; a Phase F
metric must not read these three bands.

**(f) SMAP `SPL4SMGP/008` band list is INCOMPLETE in the registry.**
Registry declares 5 bands. The catalog has ~45, including
`sm_profile`, `sm_surface_wetness`, `sm_rootzone_wetness`,
`sm_profile_wetness`, `soil_temp_layer1..6`, `land_evapotranspiration_flux`,
`heat_flux_latent`, `net_downward_shortwave_flux`, precipitation, LAI,
`vegetation_greenness_fraction`, `sm_surface_anomaly`.
**Unit is "Volume fraction" (m3/m3), min 0, max 0.9 — NOT 0..1.**
Registry declares `valid_range = (0.0, 1.0)` → **should be (0.0, 0.9)**.
Spatial resolution: catalog says **11000 m** (the registry says
"11000 m (9 km, EASE-Grid 2.0)" which is honest but the EE pixel size is
11000 m). Cadence 3-hourly confirmed. Available from 2015-03-31 confirmed.
→ Add the missing bands actually used; fix `valid_range` to 0.9.

**(g) `sm_surface_wetness` unit** — catalog: dimensionless 0..1 "relative
saturation between completely dry and completely saturated". Registry says
`"fraction"` — acceptable, but the *description* should say "relative
saturation" because it is NOT a volume fraction and the two must never be
compared or averaged together.

### Scientific decisions worth remembering
- **ERA5 sign is a NEGATION, never `abs()`, never clamped.** Stored
  negative = evaporation. Stored positive = condensation and must stay
  negative. Every statistic is mirrored (min↔max, p10↔p90, p25↔p75).
  Component ET bands are swapped in the EE asset and are never read.
- **`era5_potential_evaporation` always returns `unavailable`** — the
  sign convention is undocumented in both the catalogue and the ECMWF
  parameter database, and the unit appears to be metres rather than
  mm/day. MOD16 PET is the supported alternative.
- **MOD16 ET/PET are 8-day SUMS (scale 0.1), not daily rates.** Unit
  reported as `mm/period`. Per-composite period length is read from the
  image (`period_days` via `aggregateArray`), never assumed as 8.
- **CWSI/WDI structurally cannot carry a value** — they subclass a base
  whose `compute()` returns unavailable unconditionally.
- **SMAP retrieval_qual_flag is a bitfield, not good/bad.** bit1=1 means
  SKIPPED (not a retrieval; holds a fill value). Mask removes bit1=1;
  bit0=1 (uncertain) is kept, because it is still a real observation.
- **SMAP L3 split across two collections** (`/006` from 2023-12-04,
  `/005` before). Requesting `/006` early returns an empty set
  indistinguishable from cloud cover, so the collection is chosen from
  the request start date.
- **AM and PM overpasses are separate metrics**, never averaged (strong
  diurnal cycle).
- **Never convert `kg/m2` ↔ `m3/m3` ↔ `mm`** — needs layer thickness and
  density; all soil metrics here report `m3/m3` only.
- **ERA5 root zone thickness weights are 7 / 21 / 72 cm** (0-7, 7-28,
  28-100). Flat mean is wrong; test pins 0.135 vs a flat 0.200.

## PHASE F — gap closure: Step 3 relative saturation (2026-09-18)

Re-auditing my own Phase F work against the 15-step order found two
gaps. Both are now closed.

### Gap 1 — Step 3 (`soil_moisture_wetness`) had been silently skipped

Implemented `SoilMoistureWetnessMetric` in `soil.py`:
- key `soil_moisture_wetness`, unit **`fraction`**, scale 11 000 m,
  basis MODELLED, dataset `NASA/SMAP/SPL4SMGP/008`.
- Band `sm_rootzone_wetness`. Catalogue VERIFIED verbatim: dimensionless
  0–1, "relative saturation between completely dry conditions and
  completely saturated conditions".
- It is **RELATIVE SATURATION, not volumetric water content**. Wetness
  0.5 means halfway between the driest and wettest state, NOT half water
  by volume. Two soils at the same wetness hold different amounts of
  water. It is published as a *separate* metric from
  `soil_moisture_rootzone` and the two are never merged.

**The SoilGrids `(theta - WP)/(FC - WP)` derivation was evaluated and
DECLINED.** Three concrete reasons, all now recorded in the metric's
provenance:
1. Depth support does not line up — SMAP L4 is a 0–100 cm average;
   SoilGrids is six discrete intervals (0-5, 5-15, 15-30, 30-60, 60-100,
   100-200 cm) that do not tile the root zone evenly.
2. Different kind of quantity in space and time — SMAP is 3-hourly 11 km
   dynamically assimilated; SoilGrids is a static 250 m soil property map
   (1905–2016). The quotient would take its temporal variation entirely
   from SMAP and part of its spatial texture from a century-scale map.
3. 33 kPa is only *approximately* field capacity and 1500 kPa only
   *approximately* permanent wilting point; a derived wetness would
   inherit that approximation silently and present it as measured.

The product's own published band is both more accurate and more honest,
so it is used directly and no conversion is applied.

### Gap 2 — the GLDAS/FLDAS rejection reason is now VERIFIED

Fetched `NASA/GLDAS/V022/CLSM/G025/DA1D` and confirmed `SoilMoist_S_tavg`,

(27 830 m, daily, 2003+). This is why they cannot be silently combined
with SMAP's volume fraction — the rejection reasoning previously lived
only in prose, now it is verified against the catalogue. GLDAS and FLDAS
remain deliberately unregistered.

## Phase H audit — Terrain (evidence gathered)

Live Earth Engine was reachable once the broken sandbox proxy was bypassed:
run GEE scripts with `env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy`.

**Verified dataset facts**
- `NASA/NASADEM_HGT/001`: 3 bands — `elevation` (m, EGM96 geoid),
  `num` (source-scene index, **0–255**), `swb` (**0 = Land, 255 = Water**).
  30 m, single acquisition 2000-02-11 → 2000-02-22, static.
- `USGS/SRTMGL1_003`: `elevation` only, catalogue range **−10…6500 m**, 30 m,
  same acquisition window, role `fallback`.

**Registry defects found (not yet fixed)**
1. `swb` `valid_range=(0.0, 1.0)` — catalogue says 0 and **255**.
2. `num` `valid_range=(0.0, 100.0)` — catalogue says **0–255**.
3. `num` description "Number of source scenes" is wrong — it is a *source
   index*, where `0` specifically means water in corrected SRTM water body data.
4. SRTM `elevation` range registered as `(−500, 9000)`; catalogue says
   `(−10, 6500)`.

**Empirically established (this is the important part)**
- `ee.Terrain.aspect` is **degrees clockwise from north**, measuring the
  *downslope* direction. Proved with synthetic planes: a plane sloping down
  toward the east → aspect **90**; toward the north → aspect **0**.
- **`aspect = 0` is ambiguous** — it is both "due north" and what flat ground
  returns. `aspect_min = 0` appeared over genuinely flat terrain. So a bare
  aspect mean is meaningless without a slope mask, and 0 must never be read
  as "flat".
- Deep ocean returns **fully masked** NASADEM (`num`/`swb` null, histogram
  empty). Masked ≠ 0.
- The Caspian reads **−29 m**, confirming the EGM96 datum and that negative
  elevations are real values, not nodata.
- `ee.Terrain.fillMinima` **only works on INT types** — it silently collapsed
  a float DEM to the constant border value (10000). Unusable for TWI here.
- No `flowAccumulation`, `flowDirection`, `neighborOffset`, or
  `ee.Algorithms.Terrain` exists in `ee` 1.1.4. Confirmed by introspection.

**TWI consequence**
Flow accumulation is a *global serial* quantity; Earth Engine exposes no
primitive for it, and a correct D8 implementation needs one dependent round
trip per iteration (measured ~0.4 s each), which cannot be bounded for a
real basin. A single `focal_max(1,...)` pass is only a 1-pixel upslope proxy
and is NOT flow accumulation — using it would produce a plausible-looking,
wrong wetness index. Decision: keep TWI **unavailable** with the full
reasoning, do not fake it.

## Phase H — STEP 1 audit: the temporal-coverage contract

**The contract as it stands**

`DatasetSpec` (types.py:211) carries `available_from: str` and
`available_to: Optional[str]`, documented nowhere as to *meaning*. The only
consumer of that meaning is `Metric.can_attempt()` (base.py:257), which
calls `coverage_overlap_days()` (base.py:86) and rejects when the overlap is
zero, returning `NOT_AVAILABLE_REASON_OUT_OF_COVERAGE`.

about dates inside this window." That is correct for a time series and
wrong for a static surface.
